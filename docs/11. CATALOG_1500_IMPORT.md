## Code changes

- **Blank themes.** A row with no themes is never ranked, even if its rationale mentions a chosen interest
  (71 rows in v5; none in v6).
- **Experiences.** `experience_context` is split on pipes only: 109 of the new rows are full sentences with commas.
- **Booking words.** "Booked", "Date-confirmed", "Reserved" and similar are removed from guest text, because
  nothing has been booked or confirmed. Matching still reads the original wording.
- **Staff notes.** "Emotional fit is a hypothesis for testing" and similar stay out of guest text.
- **Goals are never merged.** Each selected goal gets its own line and its own experience. A goal with nothing
  on file gets no line; if no goal has one, the card says "Suited to restoration." for the main goal only.
- **Settings.** "Setting you asked for: forest." names only settings of the kind requested, so a city near
  mountains is not called a mountain setting.
- **Itinerary cache.** Cached by `destination_id`, so two places called Santiago in one session stay apart.
  Map, hotel and activity searches already carry the country.

## Capacity

No infrastructure change. Per ranking on a development laptop: about 100 ms at 1,000 rows and 150 ms at 1,500.
The catalogue uses about 9 MB in memory. Network calls per request do not change: the same 28 map lookups and
one photo lookup per card.

## Deployment and rollback

1. Tag the running image before anything changes: `docker tag tauhidhasansaa/arkeric88:latest tauhidhasansaa/arkeric88:v3-backup` and push it.
2. Commit, build and push the new image under `v5`. The catalogue is built into the image.
3. Run it on staging and repeat the five scenarios. Send the changes for approval.
4. Deploy `v5` to production after approval. `catalog_version.release` must read `v5`, `candidate_count` `1500`.
5. To roll back, redeploy the `v3-backup` image; `catalog_version.release` must read `v3`. No data migration is needed. Sessions created on `v5` that reference one of the 500 new IDs cannot be reopened on `v3`.
